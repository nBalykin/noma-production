# NOMA Production — сайт-портфолио

TL;DR для Claude: одностраничный сайт-портфолио музыкальной продакшн-студии. Читай этот файл вместо того, чтобы заново прояснять контекст.

## Поддержание этого файла в актуальном состоянии

Этот файл должен отражать текущее состояние проекта, а не историю. Если в ходе работы выясняется что-то, что противоречит написанному ниже (изменился факт, дизайн-решение, договорённость с клиентом, сам код стал вести себя иначе) — **обнови соответствующий раздел сразу, в рамках той же правки**, не дожидаясь отдельной просьбы. Не оставляй файл рассинхронизированным с реальным `studio-landing-mockup.html`.

## Что это и где смотреть

- **Рабочий файл:** `studio-landing-mockup.html` — единственный файл, который редактируется. Это самодостаточный HTML/CSS/JS (без сборки, без фреймворков) — открывается напрямую в браузере.
- **Опубликован как Artifact:** https://claude.ai/code/artifact/43b4380e-1745-491f-8cc2-84c249342686
  Чтобы обновить именно эту ссылку (а не создать новую): сначала `Artifact` c `action: "read"` и этим `url`, затем публиковать с тем же `url`.
- **`Main.dc.html` + `canvas.json`** — заброшенная попытка сделать интерактивный Claude Design canvas. На этой машине нет Node.js/Bun, поэтому `seed-canvas.mjs` не запускается и канвас собрать нельзя. Не трогать, не пытаться реанимировать без node/bun. Весь реальный макет живёт в `studio-landing-mockup.html`.
- Фото команды лежат в этой же папке (`Фото Никита.jpg`, `Фото Денис.PNG`, `Фото Макс.PNG`) и уже встроены в HTML как base64 (см. ниже, как добавлять новые).
- **`Pictures/`** — оригиналы обложек треков (не сжатые, полноразмерные JPG). В HTML встроены только сжатые копии (base64), оригиналы отсюда не трогаются и не удаляются — используются как источник при пересжатии.
- **`Audio/`** — сырые WAV-мастера треков от клиента (~370 МБ суммарно). **Не хостить и не коммитить как есть** — это исходники для конвертации, не то, что отдаётся посетителям сайта.
- **`Audio/web/`** — веб-версии треков, сгенерированные из WAV через ffmpeg: для каждого трека пара `<slug>.opus` (128k) + `<slug>.mp3` (192k, фолбэк для старого Safari/iOS без поддержки Opus). Именно на эти файлы ссылаются `<audio>` в HTML (`Audio/web/...`). Если клиент добавит новый трек или заменит WAV — пересобрать пару командой вида `ffmpeg -i "input.wav" -c:a libopus -b:a 128k out.opus` и `-c:a libmp3lame -b:a 192k out.mp3`.

## Стек и почему так

- Чистый HTML/CSS/JS, без React/сборщиков — сознательный выбор для лёгкого хостинга (GitHub Pages и т.п.) и чтобы клиент сам мог редактировать текст.
- Один файл, все стили инлайн + один `<style>` блок сверху с CSS-переменными и media query.
- Референс, который клиенту НЕ нравится: milkmusic.ru (светлый, «самодельный» вид, зелёные кнопки) — сайт сделан подчёркнуто иначе: тёмный, строгий, официальный.

## Дизайн-система

- Тёмная палитра, CSS-переменные в `:root`: `--bg:#0d0b12`, `--bg-elevated:#17141f`, текстовые `--text/--text-secondary/--text-tertiary/--text-quiet/--text-faint`.
- **Акцент: сложный синий `--accent:#4C63D2`** (раньше был салатовый `#b8ff3d` — клиент попросил заменить: слишком «кислотно» на чёрном фоне для премиального/строгого позиционирования под топ-артистов и лейблы). Везде используется только через переменные (`--accent`, `--accent-dim`, `--accent-soft`, `--accent-soft-2`, `--accent-bar`, `--accent-play`, `--on-accent`) — при повторной смене акцентного цвета достаточно поменять блок переменных в `:root`, руками по файлу искать не нужно. `--accent-play: rgba(76,99,210,0.65)` — добавлена 2026-09-12 по просьбе клиента сделать кружки-плеи на обложках треков и бейдж «Авторское» более прозрачными (раньше оба были на сплошном `var(--accent)`); используется в `.track-cover-play` и `.author-badge`, но НЕ в бейдже «Основная услуга» в `#pricing` — его непрозрачность не трогали, не путать эти два визуально похожих бейджа. `--on-accent` — светлый (`#f5f3f9`), т.к. этот синий средней светлоты и белый текст/иконки на нём читаются лучше тёмных.
- **Тёплые градиенты `--warm-1:#9a5a2e` / `--warm-2:#3c1f16`** — глубокое амбер/медное свечение на фоне hero (радиальный градиент за заголовком), задаёт «премиальную» глубину в паре с холодным синим акцентом. Если добавляешь новые фоновые свечения/блобы в других секциях — используй эту же пару для консистентности, а не произвольный цвет.
- Шрифты: **Unbounded** (заголовки) + **Manrope** (текст) — оба с кириллицей, из Google Fonts.
- **Главный `h1` в hero — `font-weight: 600`** (SemiBold), не 700/800: клиент просил снизить насыщенность шрифта в заголовке, Ultra-Bold/Bold в Unbounded на таком размере выглядел слишком тяжело. Остальные заголовки (`h2`) остаются на 700 — трогать их не просили.
- Стиль сознательно «строгий/официальный»: прямоугольные скругления по 6–12px (НЕ pill-кнопки), никаких ховеров с движением/подпрыгиванием (только смена цвета/яркости), минимум анимации.
- **Логотип в шапке — растровый PNG (base64), не инлайн-SVG.** `.brand-logo` — это `<a href="#top">` с одним `<img>` внутри (монограмма N + акустическая волна + текст «NOMA PRODUCTION» на прозрачном фоне, цвет шампань-золото уже запечён в самом PNG). Классов `.logo-stroke`/`.logo-text` и переменных `--logo-gold`/`--logo-gold-hover` в разметке больше нет как активно используемых — эти CSS-переменные остались объявлены в `:root`, но логотип их не читает (цвет зашит в пиксели картинки), трогать их бессмысленно, если меняешь цвет лого — нужно перегенерировать сам PNG. Если нужен только значок-монограмма отдельно от текста (напр. для фавикона) — обрежь этот же PNG по левой части (см. ниже, как это уже сделано).
  **История бага (закрыт 2026-09-11):** до этой правки в `.brand-logo` реально лежал не `<img>`, а самодельный inline-SVG с вручную набранными `d="..."` путями — CLAUDE.md уже описывал целевой PNG-вариант, но в код это тогда не попало, и SVG-путь рендерился как нечитаемая клякса вместо буквы N (эту рассинхронизацию документации и кода нашли и исправили только сейчас). Клиент прислал готовый референс-скриншот логотипа — фон обрезан по bounding box золотых пикселей и сделан прозрачным через chroma-key (PowerShell/System.Drawing), вставлен как base64 `<img>` вместо SVG. Ссылка вокруг лого была `href="/"` (битая — сайт без роутинга) — заменена на `href="#top"` (`id="top"` на `.root`).
- **Фавикон и `<title>`:** `<title>NOMA Production</title>` + три `<link>` в первых строках файла (до `<style>`) — `rel="icon" sizes="32x32"`, `rel="icon" sizes="16x16"`, `rel="apple-touch-icon" sizes="180x180"`, все с `href="data:image/png;base64,..."` (никаких отдельных файлов вроде `/favicon-32x32.png` — сайт остаётся одним самодостаточным HTML).
  **32×32 и 16×16 — не просто уменьшенная детальная монограмма, а отдельная упрощённая версия.** Прямой ресайз полной монограммы (тонкие двойные линии волны + вертикальные штрихи «N») на 16px превращался в нечитаемое пятно — клиент сам заметил это и прислал референс с более простой/жирной иконкой для маленьких размеров. Сделано так: монограмма обрезается ещё теснее — только центральная часть с буквой N (без тонких хвостов волны слева/справа, которые на квадратной маленькой иконке всё равно превращаются в обрубки), затем бинаризуется (сплошной `--logo-gold` без полутонов) и «утолщается» через штамповку копий со сдвигом по кругу (дешёвая имитация morphological dilate через `Graphics.DrawImageUnscaled` в цикле по смещениям — попиксельный blur/threshold в PowerShell на изображении такого размера считается минутами и один раз реально зависал, поэтому решали через GDI+ трюк, а не ручные циклы по пикселям), пока соседние линии не сольются в жирный сплошной силуэт. 16×16 использует более сильное утолщение (радиус ~7px на кропе), 32×32 — чуть слабее (радиус ~3px), чтобы сохранить немного текстуры волны внутри буквы. **180×180 (apple-touch-icon) — та же обрезка монограммы, что и раньше, БЕЗ упрощения** — на таком размере тонкие линии читаются нормально, упрощённая версия там не нужна и будет смотреться грубее оригинала.
  Если логотип в шапке заменят на новый — все три иконки надо перегенерировать из нового файла: 180px — обычным кропом (bounding box → центрирование → ресайз), 32/16px — через описанный выше пайплайн «обрезать core → бинаризовать → утолщить → обрезать по новому bbox → центрировать → ресайз», а не просто уменьшить детальную версию.
  **Если пришлют «сгенерируй фавикон через favicon.io/realfavicongenerator» с инструкцией по отдельным файлам:** не заводить отдельные PNG/ICO-файлы и не грузить бренд-ассет на сторонний сервис — здесь это не нужно, тот же результат (несколько размеров, apple-touch-icon) получается локально из уже готового логотипа через PowerShell, base64 прямо в HTML.
- **Кнопка `.btn-ghost` («Обсудить проект» и подобные)** — не просто обводка `var(--border-soft)` (она была почти не видна на тёмном фоне и не читалась как кликабельная). Сейчас: `border: 1px solid rgba(245,243,249,0.4)` + `background: rgba(245,243,249,0.12)` + `color: var(--text)`. При добавлении новых ghost-кнопок бери этот же паттерн (светлая полупрозрачная обводка + лёгкая заливка), а не голый `border-soft`.
- **Иконки в SERVICES STRIP** (Аранжировка / Сведение / Мастеринг) — все три должны быть выровнены по центру первой строки заголовка (не по всему текстовому блоку с описанием): `margin-top: -1.5px` на `<svg>` при `flex-shrink: 0`, проверено через `getBoundingClientRect` (была реальная просадка на 3.5px, когда margin был `2px`). У «Аранжировки» — силуэт рояля (корпус + клавиши + изогнутая ножка-стойка), контурная линия, `stroke-width: 1.5`: иконка Lucide `piano`, выбрана клиентом из 5 предложенных вариантов (Lucide/Tabler/Phosphor/Material Symbols/MDI, все MIT/Apache), заменила более раннюю абстрактную (рамка + вертикальные штрихи). У «Сведения» и «Мастеринга» — **всё ещё старые абстрактные иконки** (три вертикальных бара разной высоты / два круга с диагональной насечкой) — если план был сделать их тоже «предметными» (фейдеры микшера, ручки-потенциометры), это пока не реализовано в коде, только желание — не полагайся на это описание, свери с реальной разметкой перед правкой.
- Мобильная адаптация — основной media query `@media (max-width: 860px)` внизу `<style>`: прячет nav-links, схлопывает `.grid-2/.grid-3/.grid-4/.grid-6` в 1 колонку. Если добавляешь новый грид-блок с asymmetric padding/border между колонками (как было в SERVICES STRIP) — обязательно проверь, что он не «съезжает» при схлопывании в 1 колонку на мобильном (была реальная баг-репорт от клиента на это). **Исключение:** `#team .grid-3` (карточки команды) и `#pricing .grid-3` (карточки прайса, добавлено в карусель 2026-09-12 по просьбе клиента — «сделай так же, как карточки команды») в этом же media query не схлопываются в 1 колонку, а превращаются в горизонтальную swipe-карусель (`display: flex`, `overflow-x: auto`, `scroll-snap-type: x mandatory`, каждая карточка `flex: 0 0 78%` — видно край следующей карточки как намёк на скролл); это осознанный выбор для обеих троек карточек, не баг и не забытый кусок кода. Оба селектора шарят один и тот же блок правил (scrollbar-стили + сам flex/scroll-snap блок в media query), у `#pricing .grid-3` дополнительно `max-width: none !important; margin: 0 -22px !important;` в media query — на десктопе у этого грида инлайновые `max-width: 980px; margin: 0 auto` (центрируют 3 карточки уже полной ширины контейнера), которые на мобильной карусели надо было перебить, иначе инлайн-стили залипали поверх обычного (без `!important`) `margin: 0 -22px` из общего блока. Если добавишь третий грид с такой же каруселью — проверь, нет ли у него аналогичных инлайновых `max-width`/`margin`, которые тоже придётся перебивать `!important`.
  **Баг, найденный и исправленный в этой же сессии (2026-09-12, скриншот с реального телефона клиента):** бейдж «Основная услуга» на первой карточке прайса (`position: absolute; top: -11px; left: 22px` — «наезжает» на верхнюю рамку карточки, обычный приём для ribbon-бейджей) на мобильной карусели обрезался сверху примерно на высоту, на которую вылезает за границу карточки. Причина — не баг конкретно вёрстки бейджа, а особенность спецификации CSS overflow: если `overflow-x` не `visible` (у нас `auto`, ради горизонтального скролла), то `overflow-y: visible` браузер всё равно вычисляет как `auto`, а не оставляет как есть — то есть контейнер начинает клипать и вертикальное переполнение тоже, хотя явно об этом никто не просил. У `#team .grid-3` такой проблемы нет, потому что там ни у одного элемента нет отрицательных отступов, вылезающих за границы карточки. Фикс — `padding-top: 14px` на `#pricing .grid-3` в media query (в том же блоке, где `max-width: none !important; margin: 0 -22px !important;`): даёт бейджу пространство внутри clip-области контейнера, чтобы вылезающая часть не срезалась. Если в будущем на карточку добавится другой элемент с отрицательным `top`/`left`/`right`/`bottom` (ещё один ribbon, тень, декоративный уголок) в контейнере с `overflow-x: auto` — держи это в уме, обычным `overflow: visible` на дочернем элементе эту обрезку не отменить, нужно либо давать паддинг на контейнере, либо не заходить за его границы.
  **Кнопки «Написать нам» в шапке больше нет (убрана 2026-09-12 по прямой просьбе клиента, и на десктопе, и на мобильном).** История для контекста, если она понадобится снова: 2026-09-11 в шапке была кнопка `id="nav-cta"` рядом с лого, и под неё чинился отдельный узкий `@media (max-width: ...px)` (сначала 340, потом 380px) — она вылезала за край на экранах ≤~330px, и не имела автомата минимального зазора от лого. Весь этот код (медиа-запрос, `#nav-cta`, сама ссылка) удалён вместе с кнопкой — не пытайся реанимировать конкретные пиксельные значения оттуда, если кнопку вернут, вёрстку и брейкпоинты нужно будет продумать заново под актуальный контент шапки.
  На `.container` шапки (лого + `#nav-links`) остался `gap: 16px` — гарантирует минимальный отступ между лого и десктоп-навигацией даже если `justify-content: space-between` не даёт для этого свободного места; сейчас это чисто подстраховка, в норме на десктопе места и так много.

Обнуление (`currentTime = 0` + `resetSeek()`) происходит только по событию `ended` — трек естественно доиграл до конца, значит следующий плей должен начаться заново. Т.к. `<audio preload="none">`, у только что нажатого трека `duration` какое-то время `Infinity`/неизвестна — если утащить шкалу до того, как длительность резолвится, процент запоминается в `audio.dataset.pendingSeek` и применяется на `loadedmetadata`/`durationchange`. Если сделать градиент в `--bg` (что было в первой версии этой полосы), на стыке фото-окна и панели остаётся заметный скачок цвета — глаз считывает это как границу, даже если сама полоса размытия уже плавная. Второе условие бесшовности — у панели (4) **нет `border-top`**: раньше там стоял `border-top:1px solid rgba(245,243,249,0.08)`, и вместе с этим цветовым скачком он читался как жёсткая белёсая линия ровно там, где должен быть один непрерывный переход (клиент отдельно указал на эту линию — «слишком явный блок с текстом»). Стиль панели сейчас: `padding:14px 16px 16px; background:var(--bg-elevated); min-height:216px` — без `border-top`; (4) панель с именем/ролью/био — обычный блок в потоке, высота **минимум 216px, но растёт**, если био не помещается (не жёстко фиксированная, как было в самой первой версии, и не чистый `auto` без ограничения снизу, как в промежуточной версии того же дня). У `.grid-3` (родитель) стоит `align-items: start` — обязательно, без этого grid/flex по умолчанию растягивает все карточки на высоту самой высокой (`stretch`), а короткое био (Максим — «Микс-инженер.») оставляло бы пустой отступ внизу его карточки.
  **Почему так (было по-другому до 2026-09-12):** раньше фото было просто `background-image` НА САМОЙ `.team-photo-card` (`aspect-ratio:3/4` на всю карточку), а панель с био — `position:absolute; bottom:0; height:216px` ПОВЕРХ фото (эффект «текст на фото» через `backdrop-filter:blur`). Это давало два независимых, поочерёдно всплывших бага:
  1. **Обрезка текста (найдено 2026-09-11, скриншот с реального телефона клиента, Realme GT Neo 3T):** карточка в мобильной карусели — не фиксированная ширина, а `78%` от viewport, поэтому чем уже экран, тем на большее число строк переносится био при НЕИЗМЕННОЙ высоте панели — самое длинное био (Дениса) при 160px панели реально теряло последнюю строку через `overflow:hidden` на диапазоне ~300–375px (и даже в узком десктопном окне ~860–900px). Промежуточный фикс — поднять фиксированную высоту панели до 216px — решил обрезку, но создал вторую проблему.
  2. **Чрезмерная обрезка ФОТО на телефоне (найдено 2026-09-11/12, снова скриншот с реального телефона клиента):** раз панель абсолютно позиционирована `bottom:0` поверх карточки с `aspect-ratio:3/4` (высота = ширина карточки × 4/3), а высота панели — ФИКСИРОВАННЫЙ пиксель (216px) — на узкой мобильной карточке (~258px) эти 216px составляют гораздо БОЛЬШУЮ долю карточки, чем на широкой десктопной (~325px), и панель перекрывает пропорционально куда больше фото. На десктопе выглядело нормально (клиент подтвердил), на телефоне — фото казалось обрезанным сильнее, хотя сам `cover`-кроп физически был идентичным на обеих ширинах (просто больше его пряталось под панелью).
  **Промежуточное решение (2026-09-12, днём):** полностью развязать фото и текст, чтобы они не боролись за одно и то же пространство. Фото — независимый блок с фиксированным (в единицах ширины) видимым окном `aspect-ratio:3/2`, панель с текстом — обычный блок ниже, растёт вниз по высоте контента (`auto`). Побочный эффект: пропал визуальный приём «текст поверх фото на матовом стекле» — эта версия ушла в коммит без эффекта стекла и была проверена только вслепую (без реального рендера в браузере).
  **Правки того же дня вечером, уже с визуальной проверкой в браузере (см. также историю тредов/сессии):** клиент явно попросил вернуть эффект стекла — добавлена 56px-полоса `backdrop-filter:blur(12px)` у нижней кромки фото (см. структуру блока (3) выше) — это компромисс между «текст на стекле поверх всего фото» (старая версия, резала текст/фото) и «вообще без эффекта» (промежуточная версия): стекло чисто декоративное, на высоту панели и раскладку не влияет. Одновременно нашли, что у Дениса на фото была обрезана нижняя часть гитары — окно-глазок увеличено с `3/2` → `3/2.3` → **`3/2.8`** (подбиралось итеративно, проверялось программной вырезкой видимой области из фактического base64-фото каждой карточки и сверкой, попадает ли в кадр весь корпус гитары — обычный визуальный осмотр браузера на таком мелком элементе недостаточно точен). Побочно это же увеличение окна дало заметно больше пространства над Никитой и Максимом (у них тоже было тесновато). `min-height:216px` на панели (вместо чистого `auto`) — подстраховка, чтобы короткое био (Максим) не давало карточке провалиться ниже соседних при `align-items:start`; проверено, что ни на одной ширине 320–1400px реальный текст био не превышает 216px (текст. panel.scrollHeight ~215px по всем трём карточкам на всех проверенных ширинах) — если био станет длиннее (новый человек в команде, длиннее текст), может понадобиться поднять `min-height` или довериться `auto`-росту (он не сломан, просто сейчас не нужен).
  - Денис и Максим: фото-слой `aspect-ratio:3/4` (тот же полный кадр, что и раньше, cover/center) — окно `3/2.8` над ним показывает верхние ~2.3/4 ≈ 57% этого кадра (было ~50% при `3/2`, ~57.5% при `3/2.3` — на глаз почти то же, увеличение с `2.3` до `2.8` дало решающие дополнительные проценты именно там, где у Дениса кончается гитара).
  - **Никита:** исходник (`Фото Никита.jpg` на диске, не менялся) — 640×640 (квадрат), обрезан клиентом, но с заметным полем пустого фона НАД головой (хэдрум ~140px из 640, т.е. ~22%). Раньше здесь был двухслойный хак (размытая растянутая подложка + резкий слой), затем `height:66%`-слой внутри `aspect-ratio:3/4`-карточки (см. `git log` для деталей той итерации, если понадобится) — оба подхода были завязаны на общую высоту карточки, которая с 2026-09-12 больше не существует как единая сущность. Сейчас его фото-слой — `aspect-ratio:25/22` (математически то же самое соотношение, что давал старый `height:66%` от `aspect-ratio:3/4`-карточки: `4/3 × 0.66 ≈ 0.88 = 22/25`), т.е. **визуально идентичный кроп самого кадра**, просто выражен как независимое от общей высоты карточки соотношение сторон; а вот СКОЛЬКО от этого кадра видно в окне — растёт вместе с окном (`3/2` → `3/2.8`), так что фактически у Никиты сейчас видно заметно больше рояля и рук, чем в версии дня.

## Как добавлять/менять фото

Файлы вставляются как `background-image: url('data:image/jpeg;base64,...')` прямо в HTML (сайт — один самодостаточный файл). Т.к. base64 очень длинный, **не вставляй его вручную через Edit** — используй PowerShell:

```powershell
Add-Type -AssemblyName System.Drawing
# ресайз/сжатие в JPEG ~800-900px по стороне, quality ~80-85, если оригинал большой
# затем [Convert]::ToBase64String(bytes) и .Replace() нужного места в файле через
# [System.IO.File]::ReadAllText/WriteAllText с New-Object System.Text.UTF8Encoding($false)
# (важно: без BOM, иначе кириллица может испортиться)
```

Смотри историю правок в этом же чате/сессии как пример точных команд (ресайз фото Дениса, вставка фото Никиты, вставка фото Максима — обычный `cover`, ресайз до 900px, quality 85).

## Хостинг (уже обсуждено с клиентом, решение принято)

Рекомендовано и согласовано: **GitHub Pages** как основной хостинг (бесплатно, статике достаточно), домен покупается отдельно у любого регистратора и направляется DNS-записями. Клиент сказал, что готов немного разобраться с git.

**Аудио — статус изменился.** Изначально была договорённость не хостить аудио/видео самим, а встраивать плееры (Яндекс.Музыка/VK/YouTube). Клиент прислал реальные WAV-мастера треков и попросил подключить прямо на сайте — сейчас превью треков в портфолио играют самостоятельно захостенные Opus/MP3 (см. `Audio/web/` выше), а не внешние плеер-виджеты. Суммарный вес `Audio/web/` — около 55 МБ на 14 треков (сжаты из ~370 МБ WAV), это уже приемлемо для GitHub Pages. Сырые WAV-мастера (`Audio/`) коммитить не нужно — это чистые исходники, не то, что должно попасть в репозиторий/на хостинг. Если клиент решит вернуться к идее внешних плееров вместо самостоятельного хостинга — заменить `<audio>`-блоки на iframe-виджеты, структура портфолио (список треков) от этого не изменится.
